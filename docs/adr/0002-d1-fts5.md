# ADR 0002: Full-text search on D1 with FTS5

This is an architecture decision record (ADR). It records how bookmark search uses FTS5, SQLite's full-text search extension, on Cloudflare D1.

- Status: The tokenizer, schema, query builders, ranking, and export sequence are decided from local evidence. Whether remote D1 behaves the same, and what it bills, waits for the owner's remote run (see [Pending remote run](#pending-remote-run)).
- Issue: #4
- Date: 2026-10-29

## Summary

Bookmark search uses an FTS5 external content table, which is a full-text index that reads its text from the `bookmarks` table. It uses the `porter unicode61` tokenizer, and three triggers keep it in step with the table.

User input is split on whitespace. Pieces with no letters or digits are dropped, and every remaining token is wrapped in double quotes, so no FTS5 operator can reach the parser. The last token becomes a prefix only when it has at least three letters or digits.

Results are ordered by the hidden `rank` column, which the index is told to compute as BM25 (the ranking function FTS5 ships with) with the column weights title 10, domain 4, description 2, and note 6. The FTS5 documentation says ordering by `rank` is faster than calling `bm25()` in `ORDER BY`, and locally both gave the same rows in the same order. Local row counts also came out lower for `rank`, but the local counter cannot see FTS5's internal work, so that difference is not evidence about billing.

All local numbers below were measured with wrangler 4.151.0 and its bundled Miniflare and workerd. No remote D1 database was created, so every remote result is marked pending. The generated SQL and the raw results are committed in [`0002-d1-fts5/`](0002-d1-fts5/); the scripts that produced them are not (see [Reproducing the numbers](#reproducing-the-numbers)).

## Context

Issue #8 writes the real migration and the search endpoint. Issue #13 adds a gate that skips the meaning search when the strict text query returns between 1 and `STRICT_SKIP_MAX` (5 to start) results. Both need four things settled first:

- which tokenizer D1 accepts, and which one to use;
- how many rows each operation reads and writes, because D1 bills by rows;
- how to turn user text into a safe `MATCH` string;
- how to export a database that contains a virtual table.

## Decision

### Schema

The FTS5 statements follow the external content example in the FTS5 documentation, section 4.4.3. The `rank` option comes from section 6.11, and `UPDATE OF` from the SQLite `CREATE TRIGGER` documentation. The `bookmarks` table here is the spike's stand-in; issue #8 owns the real columns, such as `normalized_url` and `compact`.

```sql
CREATE TABLE bookmarks (
  id INTEGER PRIMARY KEY,
  url TEXT NOT NULL UNIQUE,
  title TEXT NOT NULL,
  domain TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  note TEXT NOT NULL DEFAULT ''
);

CREATE VIRTUAL TABLE bookmarks_fts USING fts5(title, domain, description, note, content = 'bookmarks', content_rowid = 'id', tokenize = 'porter unicode61');

-- Column weights, in column order: title 10, domain 4, description 2, note 6.
INSERT INTO bookmarks_fts (bookmarks_fts, rank) VALUES ('rank', 'bm25(10.0, 4.0, 2.0, 6.0)');

CREATE TRIGGER bookmarks_ai AFTER INSERT ON bookmarks BEGIN
  INSERT INTO bookmarks_fts (rowid, title, domain, description, note)
  VALUES (new.id, new.title, new.domain, new.description, new.note);
END;
CREATE TRIGGER bookmarks_ad AFTER DELETE ON bookmarks BEGIN
  INSERT INTO bookmarks_fts (bookmarks_fts, rowid, title, domain, description, note)
  VALUES ('delete', old.id, old.title, old.domain, old.description, old.note);
END;
CREATE TRIGGER bookmarks_au AFTER UPDATE OF title, domain, description, note ON bookmarks BEGIN
  INSERT INTO bookmarks_fts (bookmarks_fts, rowid, title, domain, description, note)
  VALUES ('delete', old.id, old.title, old.domain, old.description, old.note);
  INSERT INTO bookmarks_fts (rowid, title, domain, description, note)
  VALUES (new.id, new.title, new.domain, new.description, new.note);
END;
```

The `rank` option is stored in the shadow table `bookmarks_fts_config`, so it lives and dies with the index. It survived `rebuild`, but dropping `bookmarks_fts` erased it (see [Column weights and the rank option](#column-weights-and-the-rank-option)). Every script that recreates the index must set it again.

`UPDATE OF` names the indexed columns, so an update that changes only `url` no longer touches the index. The SQLite documentation warns that it silently ignores column names that do not exist, so issue #8 should keep the list in step with the FTS5 columns.

### Quoting function and query builders

Issue #8 can copy the code below as it is; it is the full text of the module the spike ran. The grammar comes from the FTS5 documentation:

- section 3.1: a string is enclosed in double quotes, and an embedded `"` is escaped by doubling it;
- section 3.3: a `*` after a string marks its last token as a prefix token;
- section 3: phrases joined by a space are an implicit `AND`, and phrases can be joined with `OR`;
- section 4.3.1: the default tokenizer keeps the Unicode categories `L*`, `N*`, and `Co` (letters, numbers, and private-use characters) and treats everything else as a separator.

```ts
const TOKEN_CHARACTER = /[\p{L}\p{N}\p{Co}]/gu;
const MIN_PREFIX_CHARACTERS = 3;

function countTokenCharacters(token: string): number {
  return token.match(TOKEN_CHARACTER)?.length ?? 0;
}

/** Split on whitespace and drop pieces the tokenizer would turn into nothing, such as `-` or `"`. */
export function splitSearchInput(input: string): string[] {
  return input.split(/\s+/u).filter((token) => countTokenCharacters(token) > 0);
}

/** One FTS5 string literal: wrap in double quotes and double any embedded quote. */
export function quoteFtsToken(token: string): string {
  return `"${token.replaceAll('"', '""')}"`;
}

/** The quoted tokens joined by a space, without a prefix marker. */
export function quoteFtsInput(input: string): string {
  return splitSearchInput(input).map(quoteFtsToken).join(" ");
}

function buildMatch(input: string, separator: string): string | null {
  const tokens = splitSearchInput(input);
  if (tokens.length === 0) {
    return null;
  }
  const quoted = tokens.map(quoteFtsToken);
  const lastIndex = quoted.length - 1;
  // A short last token as a prefix matches nearly every row (`"c"*`, `"a"*`).
  if (countTokenCharacters(tokens[lastIndex]) >= MIN_PREFIX_CHARACTERS) {
    quoted[lastIndex] = `${quoted[lastIndex]}*`;
  }
  return quoted.join(separator);
}

/** Every token must match: FTS5 reads phrases separated by a space as AND. */
export function buildStrictMatch(input: string): string | null {
  return buildMatch(input, " ");
}

/** Any token may match. */
export function buildLooseMatch(input: string): string | null {
  return buildMatch(input, " OR ");
}
```

There are three rules on top of plain quoting, and each one answers a measured problem:

| Rule                                                                  | Problem it answers (porter, 200 rows)                                                                                                         | Example                                                                  |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Drop tokens with no letters or digits                                 | A punctuation-only token such as `-` becomes an empty phrase, which the `AND` drops silently, so the strict query is no longer "every token". | `snapdom -` used to send `"snapdom" "-"*`; it now sends `"snapdom"*`.    |
| Add `*` only when the last token has at least three letters or digits | A short prefix matches nearly everything: `"a"*` matched 200 of 200 rows and `"c++"*` (which tokenizes to the prefix `c`) matched 185.        | `c++` now sends `"c++"`, which matched 1 row.                            |
| Return `null` when no token is left                                   | An empty `MATCH` string is an FTS5 syntax error.                                                                                              | `""`, `"   "`, `"`, `-`, and `*` all return `null`, so no query is sent. |

`quoteFtsInput` is the function the issue's acceptance criterion describes: for `NOT "x" title:y` it returns exactly `"NOT" """x""" "title:y"`, with no prefix marker. The builders then add the marker, so the strict builder sends `"NOT" """x""" "title:y"*`. Both forms ran without an error. A test in issue #8 written from the criterion should call `quoteFtsInput`.

The character count is taken before stemming and uses the JavaScript Unicode tables, which are newer than the Unicode 6.1 tables the tokenizer uses. For ordinary text the two agree; a character added to Unicode after 6.1 could be counted here and then discarded by the tokenizer.

### Search statements

Bind the builder's output as the only parameter. The gate query in issue #13 only needs to know whether there are more than five strict results, so it asks for six:

```sql
-- Strict gate (issue #13): 0, 1 to 5, or "more than 5".
SELECT bookmarks_fts.rowid AS id
FROM bookmarks_fts
WHERE bookmarks_fts MATCH ?1
ORDER BY rank
LIMIT 6;

-- Text results (issue #8).
SELECT b.id, b.title, rank AS score
FROM bookmarks_fts
JOIN bookmarks AS b ON b.id = bookmarks_fts.rowid
WHERE bookmarks_fts MATCH ?1
ORDER BY rank
LIMIT 100;
```

### The score's sign and how to normalise it

`rank` and `bm25()` are negative, and a lower (more negative) value is a better match. The FTS5 documentation, section 5.1.1, says FTS5 multiplies BM25 by -1 so that `ORDER BY rank` in ascending order puts the best match first. Issue #8 normalises against the best hit like this:

```ts
// rows are ordered by rank, so rows[0] holds the most negative score.
const bestRank = rows[0].score;
const text = row.score / bestRank; // 1 for the best hit, smaller for worse hits
```

Both values are negative, so the ratio lies between 0 and 1. The loose query for `css container queries` (porter, weighted) gave these values:

| Bookmark                                            | `rank`  | `text = rank / bestRank` |
| --------------------------------------------------- | ------- | ------------------------ |
| 6, `CSS container queries - CSS \| MDN`             | -17.534 | 1.000                    |
| 11, `Shadow DOM v1 - Self-Contained Web Components` | -10.246 | 0.584                    |
| 32, `Practical Postgres queries`                    | -7.932  | 0.452                    |

Dividing the other way (`bestRank / row.score`) gives values above 1, and comparing with `>` treats the worst match as the best. Both mistakes are easy because the numbers are negative.

### Export

`wrangler d1 export` refuses a database with a virtual table. An export therefore drops the triggers and the index, exports, and then recreates the index, sets the `rank` option again, recreates the triggers, and rebuilds the index. The sequence is in [Export](#export) and ran successfully locally, including a restore into an empty database.

## Evidence

### How the numbers were measured

The spike ran in a throwaway directory outside the repository, with 200 synthetic bookmarks in three local databases, one per tokenizer. Twenty bookmarks were written by hand as the targets of the sample queries; for example, id 1 is `SnapDOM`, id 2 is `Squoosh`, and id 7 is `Centering in CSS: A Complete Guide`. The other 180 were generated from shared word lists, such as `Notes on the DOM` or `Deep dive into image formats`, so that the targets have competition. The rows are in [`sql/seed.sql`](0002-d1-fts5/sql/seed.sql).

wrangler's local JSON output does not carry row counts. In wrangler 4.151.0, `executeLocally()` builds each result with `meta: { duration: result.meta?.duration }` (`wrangler-dist/cli.js`, line 237807), so `wrangler d1 execute --local --json` prints only `duration`. Remote runs print the full `meta`. To read `meta.rows_read` and `meta.rows_written` locally, and to bind `MATCH ?1`, the spike script called the same Miniflare D1 binding that wrangler uses, built with the same options as `executeLocally()`. Every behaviour check (tokenizers, the rank option, quoting, prefix, boundary, rebuild, export) was also run through `wrangler d1 execute --local` or `wrangler d1 export --local`, by [`steps-1-create.sh`](0002-d1-fts5/steps-1-create.sh) and [`steps-2-checks.sh`](0002-d1-fts5/steps-2-checks.sh).

#### Which local numbers stand in for remote billing

The local counter comes from workerd's SQLite cursor, through Miniflare's D1 worker (`miniflare/dist/src/workers/d1/database.worker.js`, the `rows_read: cursor.rowsRead` line). It counts what the outer SQL statement touches, and it does not count the reads and writes that FTS5 makes in its own shadow tables. The clearest case is `rebuild`: it reads all 200 content rows and rewrites the index, but the counter reported 0 rows read and 1 row written.

This also explains why `rank` looks cheaper. With `ORDER BY rank`, FTS5 scores and sorts the matches inside the virtual table, where the counter cannot see the work. With `ORDER BY bm25()`, SQLite calls the function and sorts the rows itself, and the counter sees each row. The gap between them may be a counting artefact rather than a saving on the bill.

| Local number                                                                         | Trustworthy proxy for remote billing? | Why                                                                                                 |
| ------------------------------------------------------------------------------------ | ------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Plain table reads, such as a full scan                                               | Yes                                   | A full scan of 200 rows read 200 rows, which matches the pricing page's 5,000-row example.          |
| Index entries on insert                                                              | Probably                              | The `UNIQUE` index on `url` added one write per insert, as the pricing page describes.              |
| Any number that involves `bookmarks_fts`                                             | No, treat it as a floor               | FTS5's shadow-table work is invisible to the counter, as `rebuild` shows.                           |
| `rank` against `bm25()`                                                              | No                                    | The two orderings put the work in different places, and only one of them is visible to the counter. |
| Strict against loose, and growth with the number of matches, under the same ordering | Yes, for direction                    | Both sides are counted the same way, but the remote ratio may differ.                               |

### Column weights and the rank option

With the option set, `ORDER BY rank` returned the same rows in the same order, with the same score on every row, as `ORDER BY bm25(bookmarks_fts, 10.0, 4.0, 2.0, 6.0)`. The check covered all 42 strict and loose queries built from the sample queries, at `LIMIT 100`, on all three tokenizers. Against unweighted `bm25(bookmarks_fts)` the order matched in only 30 of 42 queries with porter, so the option is in effect.

| Step (porter)                                              | Stored `rank` option        | `rank` matches weighted `bm25()`                     |
| ---------------------------------------------------------- | --------------------------- | ---------------------------------------------------- |
| After `CREATE VIRTUAL TABLE` and the option                | `bm25(10.0, 4.0, 2.0, 6.0)` | 42 of 42                                             |
| After `rebuild`                                            | `bm25(10.0, 4.0, 2.0, 6.0)` | 42 of 42                                             |
| After dropping and recreating the index without the option | none                        | 30 of 42; it matches unweighted `bm25()` in 42 of 42 |
| After setting the option again                             | `bm25(10.0, 4.0, 2.0, 6.0)` | 42 of 42                                             |

Trigram and the default tokenizer gave the same results, except in the third row, where the recreated index without the option matched weighted `bm25()` in 30 and 31 of 42 queries respectively.

### Row accounting at 200 rows

These are local counts with porter. Trigram and the default tokenizer gave the same numbers for the four operations. Each search joins `bookmarks` to fetch the title, except the gate query. Every number that involves `bookmarks_fts` is a floor, for the reason given above.

| Operation                                               | rows_read | rows_written |
| ------------------------------------------------------- | --------- | ------------ |
| Insert one bookmark (fires `bookmarks_ai`)              | 1         | 3            |
| Update `title` and `description` (fires `bookmarks_au`) | 1         | 3            |
| Update `url` only (`bookmarks_au` no longer fires)      | 1         | 2            |
| Delete one bookmark (fires `bookmarks_ad`)              | 1         | 2            |
| `rebuild`                                               | 0         | 1            |

The insert's three writes are the table row, the `url` index entry, and one row for the FTS5 table. A comparison against a table without the index and without FTS5 showed one write, then two ([`results/out-decompose.txt`](0002-d1-fts5/results/out-decompose.txt)). Before the trigger named its columns, a `url`-only update cost 4 writes; with `UPDATE OF` it costs 2 (the table row and the `url` index), and the index still found the row afterwards.

The three-word query `css web components` had 6 strict matches and 81 loose matches. The `rank` and `bm25()` columns are local counts that cannot be compared with each other for billing:

| Query                                   | `LIMIT` | `ORDER BY rank` | `ORDER BY bm25(..., 10.0, 4.0, 2.0, 6.0)` |
| --------------------------------------- | ------- | --------------- | ----------------------------------------- |
| Strict `"css" "web" "components"*`      | 6       | 11              | 18                                        |
| Strict                                  | 50      | 12              | 18                                        |
| Loose `"css" OR "web" OR "components"*` | 6       | 11              | 243                                       |
| Loose                                   | 50      | 99              | 243                                       |
| Loose                                   | 100     | 162             | 243                                       |

Under `bm25()`, the count grew with the number of matches and not with `LIMIT`: three rows per match, so 6 matches read 18 rows and 81 matches read 243. Under `rank`, the count followed the number of rows returned. Unweighted `bm25()` read the same numbers as weighted `bm25()`.

#### Daily free-plan budget

The Workers Free plan includes 5,000,000 rows read and 100,000 rows written per day (D1 pricing page). The table assumes the worst observed case for every search: the strict gate query runs with `LIMIT 6`, and the loose query runs with `LIMIT 100`. Both orderings use the same limits. The gate figures were measured with the join to `bookmarks`, so the gate statement above, which has no join, should read fewer rows.

| Daily load                      | Per operation (worst observed, local) | Per day              | Share of the free limit                                                                             |
| ------------------------------- | ------------------------------------- | -------------------- | --------------------------------------------------------------------------------------------------- |
| 100 searches, `ORDER BY rank`   | 11 (gate) + 199 (loose) = 210 reads   | 21,000 reads         | 0.42 % of reads, a local floor: FTS5's own reads are not counted and the remote figure is pending   |
| 100 searches, `ORDER BY bm25()` | 21 (gate) + 582 (loose) = 603 reads   | 60,300 reads         | 1.2 % of reads, a local floor: FTS5's own reads are not counted and the remote figure is pending    |
| 50 saves (inserts)              | 1 read, 3 writes                      | 50 reads, 150 writes | 0.15 % of writes, a local floor: FTS5's own writes are not counted and the remote figure is pending |

Issue #8's real table adds an index on `updated_at`, so each save there will cost at least one more write. The growth matters more than the figures at 200 rows: if remote D1 bills the way the local counter sees `bm25()`, a broad loose query costs about three reads per match, so at 5,000 bookmarks one query that matches most of them would cost thousands of reads. Issue #8 should check rows read against the remote figures once they exist, not against these local ones.

### Prefix query

`"snapd"*` returned exactly one row, `SnapDOM`, on all three databases, both through the bound Miniflare query and through `wrangler d1 execute --local`.

The prefix marker interacts badly with stemming. The porter stemmer indexes `searching` as `search` and `centering` as `center`, so a prefix that runs past the stem finds nothing ([`results/out-tokenizer-probes.txt`](0002-d1-fts5/results/out-tokenizer-probes.txt)):

| Prefix         | `porter unicode61` | Default | `trigram` |
| -------------- | ------------------ | ------- | --------- |
| `"searchi"*`   | 0                  | 21      | 21        |
| `"centeri"*`   | 0                  | 1       | 1         |
| `"capturin"*`  | 0                  | 23      | 23        |
| `"searching"*` | 22                 | 21      | 21        |
| `"snapd"*`     | 1                  | 1       | 1         |

No issue plans search as the user types, and a submitted query rarely ends in a half-typed word. In the loose query the other tokens still match, and in the gate a half-typed word gives zero strict results, which falls through to the full search, so it fails safe. This trade-off is accepted. The benchmark in issue #19 should watch for it.

### Boundary: a 32,769-byte token

FTS5 truncates tokens silently. A bookmark whose note is 32,768 `a` characters followed by `b` (32,769 bytes) was inserted without an error, through `wrangler d1 execute --local --file` and through a bound parameter, and `length(note)` returned 32,769. A query for 32,768 `a` characters followed by `c` then matched that row with `porter unicode61` and with the default tokenizer, which means only the first 32,768 bytes were indexed. This confirms the FTS5 documentation, section 4.3.5. With `trigram` the same query did not match, because trigram tokens are three characters long and never reach the limit.

### Export

With the index present, every whole-database export failed locally:

```text
$ npx wrangler d1 export fts-porter --local --output exports/with-index.sql
✘ [ERROR] D1_ERROR: Failed to parse body as JSON, got: Error: D1 Export error: cannot export databases with Virtual Tables (fts5)
```

`--no-data` failed with the same error. `--table bookmarks` succeeded locally even with the index present, and the file held only the `bookmarks` table and its 200 rows, without the triggers. It succeeded because Miniflare's export skips every table outside the `--table` list before it checks for `CREATE VIRTUAL TABLE` (`database.worker.js`, lines 31 to 41). That check is Miniflare's reimplementation, not D1's, so the remote error text and the remote `--table` behaviour are pending. If the remote run confirms the `--table` behaviour, a backup could skip the drop and recreate steps.

Dropping only the virtual table is not enough. The export then succeeds, but it contains the three triggers, and the next insert fails with `no such table: main.bookmarks_fts`. The sequence that succeeded drops the triggers too:

```sh
# 1. Drop the triggers and the index. sql/drop-fts.sql holds:
#    DROP TRIGGER bookmarks_ai; DROP TRIGGER bookmarks_ad; DROP TRIGGER bookmarks_au; DROP TABLE bookmarks_fts;
npx wrangler d1 execute fts-porter --local --file sql/drop-fts.sql
# 2. Export.
npx wrangler d1 export fts-porter --local --output exports/porter.sql
# 3. Recreate the index, set the rank option, recreate the triggers, and rebuild.
npx wrangler d1 execute fts-porter --local --file sql/fts-porter.sql
# 4. Check that the index matches the table.
npx wrangler d1 execute fts-porter --local --command "INSERT INTO bookmarks_fts (bookmarks_fts, rank) VALUES ('integrity-check', 1)"
```

[`sql/fts-porter.sql`](0002-d1-fts5/sql/fts-porter.sql) holds the `CREATE VIRTUAL TABLE` statement, the `rank` option, the three triggers, and `INSERT INTO bookmarks_fts (bookmarks_fts) VALUES ('rebuild');`. Step 1 erases the `rank` option along with the index, which is why step 3 sets it again. After step 4, the stored option read `bm25(10.0, 4.0, 2.0, 6.0)` and `"snapd"*` returned `SnapDOM`. Running `exports/porter.sql` and then `sql/fts-porter.sql` against an empty database (`fts-restore`) restored 200 bookmarks, a working index, and the option.

`rebuild` and `integrity-check` with `rank` set to 1 both succeeded on all three databases.

### Strict and loose queries on the sample queries

The strict query joins tokens with a space and the loose query joins them with `OR`. Both are ranked by `rank` with the weights. The ids are bookmark ids; ids above 20 are generated filler rows. The "Unweighted top five" column repeats the loose top five under unweighted `bm25()`, to show what the weights changed.

#### What the weights changed

The weights changed the porter loose top five for 7 of the 21 queries, and in one of them the intended bookmark fell out. For `make images smaller`, Squoosh was fifth without weights and twelfth with them. Squoosh matches only in its description (weight 2), while filler rows such as id 165, `A guide to Docker images` with the note `Read later: making files smaller for the web`, match in the title (weight 10) and the note (weight 6). That filler text is synthetic, but the pattern is real: a bookmark whose name does not contain the query's words relies on its description, which carries the lowest weight. With the weights, the intended bookmark was in the loose top five for 20 of 21 queries with porter (21 of 21 without them), 21 of 21 with trigram, and 20 of 21 with the default tokenizer.

In the worked example below, SnapDOM moved from second to third. No other intended bookmark changed position in a way that moved it in or out of the top five.

The weights come from the plan and are kept. The benchmark in issue #19 should measure them against the owner's bookmarks, and lowering the gap between the title and the description is the first thing to try if real queries show the same pattern.

#### The gate evidence is weak

A strict count between 1 and 5 contained the intended bookmark 12 of 12 times with porter (5 natural-language queries and 7 name queries), 15 of 15 with trigram, and 12 of 12 with the default tokenizer. That sounds stronger than it is, for three reasons:

- every in-range strict count was exactly 1, so the sample says nothing about whether a count of 2 to 5 can be trusted;
- the same person wrote the queries and the 20 target bookmarks, and only 20 of the 200 rows were written by hand;
- the 7 name queries are single tokens, so for them the strict and the loose query are the same query.

The one count above 5 was `make images smaller` (7 results, the intended bookmark among them). With the gate query's `LIMIT 6`, it returned 6 rows, which reads as "more than 5" and falls through to the full search.

FTS5 has no stop words, so `a`, `as`, `an`, `to`, and `how` must all appear in a bookmark for the strict query to match. That is why 8 of the 14 natural-language queries returned zero strict results with porter. Zero falls through, so this costs a meaning search but loses no result.

#### Worked example: `turn html into a picture`

On all three tokenizers the strict query `"turn" "html" "into" "a" "picture"*` returned zero results, and the loose query found SnapDOM, in third place with porter, behind htmx and Tailwind CSS. The loose match came from `html`, `into`, and `a`, not from `picture`, which appears in no bookmark. A phrasing that shares no word with the bookmark would find nothing in either query, which is why zero strict results must fall through to the full search, including the meaning search, rather than being treated as a confident answer.

### Why `porter unicode61`, and why the choice is close

The choice between porter and the default tokenizer rests on very little. Without weights, porter found the intended bookmark in the loose top five for 21 of 21 queries and the default tokenizer for 20 of 21; the difference is one query (`how to center a div`, which needs `centering` stemmed to `center`). With the weights, both found 20 of 21, each missing a different query. Porter is kept because stemming helps complete words in natural-language queries, which are the queries this search is built for, and because its known weakness, a half-typed last word, fails safe. Switching later costs only dropping and recreating the index with the [export sequence](#export) steps 1 and 3, so the benchmark in issue #19 should compare porter with the default tokenizer on the owner's bookmarks.

`trigram` had the best gate numbers, but for an accidental reason: a phrase shorter than three characters matches nothing on its own and is ignored inside an `AND`, so `a`, `as`, and `vs` drop out of the strict query. The same rule makes two-character names unsearchable: `"vs"` alone returns zero rows, and by the same rule so would `go`, `js`, `ui`, or `d1`. Trigram also matches inside words, so the quoted token `"NOT"` matched 22 bookmarks, for example every title that starts with `Notes on`.

## Consequences

- Issue #8 uses the schema, `quoteFtsInput`, the builders, and the search statements above. It binds the `MATCH` string as a parameter and never builds SQL from user text. Its acceptance test for `NOT "x" title:y` should call `quoteFtsInput`.
- Issue #8 normalises the score as `rank / bestRank`, where `bestRank` is the most negative value in the result.
- Every script that creates or recreates `bookmarks_fts`, including the export sequence and any backup, must set the `rank` option and drop and recreate the triggers along with the index.
- Issue #13's gate uses `LIMIT 6`. The local sample supports it only weakly: every in-range strict count was exactly 1, and the sample was written by the same person as its targets. The benchmark in issue #19 must re-test the 1-to-5 gate on the owner's real bookmarks, where counts of 2 to 5 will occur, and should also compare porter with the default tokenizer and check the column weights.
- A partially typed last word can miss with porter stemming. This is accepted for submitted queries, and it fails safe in the gate.
- The row counts that involve FTS5 are floors until the remote run reports what D1 bills, and the local `rank` against `bm25()` difference says nothing about billing.
